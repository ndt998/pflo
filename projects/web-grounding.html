From Question to Web-Grounded Answer

A step-by-step interactive guide to how an LLM agent searches, fetches, filters, and uses web information.
Author: NDT-PRD Format: Interactive learning explainer Domain: Web-grounding, Legal tech, Academic scraping Built with: HTML, CSS, JavaScript & KaTeX

Abstract

A base LLM cannot directly open a website by itself. In a tool-enabled system, an external harness gives the model access to search, browser, extraction, ranking, and citation tools. This page separates those responsibilities and demonstrates one common retrieval workflow. The formulas are teaching models—not universal formulas used by every product.

Web-grounded agent = LLM + Harness
The LLM proposes language and tool calls; the harness executes tools, enforces rules, and returns observations.

1. The Correct Mental Model

The phrase “the LLM searches the web” is convenient but incomplete. The model itself predicts tokens. A surrounding application—the harness—decides which tools are available, sends the model’s structured request to a tool, and places the returned information back into the conversation context.

Inside the LLM

  • Interprets the prompt
  • Produces text or a structured tool call
  • Reasons over tool results placed in context
  • Generates the final answer token by token

Outside the LLM: Harness

  • Defines tools and permissions
  • Runs search, browser, API, or database calls
  • Cleans, ranks, truncates, and formats results
  • Handles retries, safety, logging, and citations
Important correctionA tool call is not proof that the model measured a calibrated “internal confidence score.” Some systems train the model to choose tools; others use rules, classifiers, or application policies. The exact mechanism is implementation-dependent.

3. When Should the System Use a Tool?

There is no single universal formula. For teaching, we can model a retrieval gate using observable task signals: freshness need, specificity, source requirement, and risk of answering without verification.

Illustrative retrieval-gate scoreTeaching model—not universal
G = w_f F + w_s S + w_c C + w_r R; use a tool if G ≥ τ
F freshness need
S specificity / niche detail
C need for citations or direct sources
R risk if the answer is wrong
w task-specific weights; sum to 1
τ tool-use threshold
Worked example. Suppose F=1.00, S=0.70, C=0.90, R=0.60; weights are 0.35, 0.20, 0.25, 0.20. Then G = 0.35×1.00 + 0.20×0.70 + 0.25×0.90 + 0.20×0.60 = 0.835. If τ=0.65, the system uses a retrieval tool.

4. Query Reformulation

The user’s sentence may be searched directly, but many systems first rewrite it into a shorter or more targeted query. The rewrite may add dates, preserve key entities, or request authoritative sources. It must not silently change the user’s intent.

Common failureOver-aggressive rewriting can remove context or introduce assumptions. Systems often keep the original user question alongside the rewritten query.

5. Ranking Search Results

Search providers already rank results. An agent may then apply a second-stage ranking or filtering step using relevance, source authority, freshness, and content quality. The weights depend on the task.

Illustrative result scoreTeaching model—not universal
S_result = 0.40R + 0.25A + 0.20F + 0.15Q
R query relevance
A source authority
F freshness
Q content quality / extractability
Worked example. For R=0.90, A=0.95, F=0.80, Q=0.85: S = 0.40×0.90 + 0.25×0.95 + 0.20×0.80 + 0.15×0.85 = 0.885. With a threshold of 0.75, this result is retained.

6. Fetching and Extracting Useful Content

After choosing a source, the harness must identify the document type before extracting evidence. HTML pages, digitally generated PDFs, and scanned documents require different pipelines. Using the wrong route can scramble reading order, lose tables, or produce OCR errors that look plausible.

</>

HTML or API response

Parse the DOM or structured payload, remove boilerplate, and preserve headings, links, dates, and provenance.

PDF

Structured PDF

Reuse the embedded text layer, but reconstruct reading order, columns, headings, footnotes, and tables from layout information.

OCR

Scanned PDF or image

Render pages as images, run OCR, retain coordinates and confidence signals, then verify uncertain numbers, dates, names, and legal citations.

Structured PDFs, scans, and OCR uncertainty

A structured PDF may already contain selectable text, yet its internal order can differ from the visual page. A two-column article may be read across columns, and tables may collapse into an unusable sequence. A scanned PDF has no reliable text layer, so OCR is necessary—but OCR output is an estimate, not a guaranteed transcription.

Why OCR errors are dangerousSmall substitutions such as 0/O, 1/I/l, or 5/S can change article numbers, dates, monetary amounts, case identifiers, and citations. Confidence values are engine-specific and may not be calibrated as true probabilities of correctness.

7. Hybrid Retrieval, Chunking, and Reranking

Long documents are usually divided into retrievable units. Production search commonly combines exact lexical matching, semantic vectors, metadata filters, and a reranking stage. Each component solves a different problem: keywords preserve exact terms; vectors improve semantic recall; filters enforce constraints; rerankers inspect the strongest candidates more carefully.

Semantic similarity with embeddings

Cosine similarityStandard mathematical definition
cos(θ) = (q · d) / (||q|| ||d||)
q query embedding
d document-chunk embedding
q·d dot product
||q|| vector length (Euclidean norm)
Worked example. Let q=(1,2) and d=(2,1). Dot product = 1×2 + 2×1 = 4. Both vector lengths are √5. Therefore cosine similarity = 4/(√5×√5) = 4/5 = 0.80.

Hybrid Search: lexical precision + semantic recall

Lexical search is strong for exact names, article numbers, rare terminology, quoted phrases, and identifiers. Semantic search is strong when the same idea is expressed with different wording. Hybrid Search retrieves with both and merges the ranked lists, often before applying metadata filters and a reranker.

How this appears in current search platformsPlatforms such as Elasticsearch and Pinecone support hybrid retrieval patterns that combine lexical and semantic signals. Their indexing, fusion, filtering, and reranking interfaces differ, so “Hybrid Search” describes an architectural pattern rather than one identical formula across products.
Reciprocal Rank Fusion (RRF)Common rank-fusion method
RRF(d) = Σ 1 / (k + rank_m(d))
M retrieval methods, such as lexical and vector search
rankₘ(d) document d's position in method m
k smoothing constant that reduces the impact of rank gaps
Worked example. With k=60, a document ranked 2nd lexically and 5th semantically receives RRF = 1/(60+2) + 1/(60+5) ≈ 0.03151. RRF combines positions, not incomparable raw scores.

Cross-Encoders: read the query and document together

Bi-encoder / embedding retriever

Encodes the query and documents separately. Document vectors can be precomputed, making retrieval fast across large collections.

Cross-Encoder / reranker

Reads each query–document pair jointly, allowing token-level interaction across both texts. It is usually more expensive, so it reranks only the top candidates.

Conceptual Cross-Encoder scoreConceptual form
s_CE(q,d) = fθ([CLS] query [SEP] document [SEP])
Worked example. Candidate A is ranked 1st by the fast retriever but receives a Cross-Encoder score of 0.62. Candidate B starts at rank 3 but receives 0.93 because its passage directly answers the query. The reranker moves B above A. The score is model-specific and should not automatically be read as a calibrated probability.
Illustrative chunk utility scoreTeaching model—not universal
U(c)=0.65 semantic(c)+0.20 source(c)+0.15 freshness(c)
Worked example. If semantic=0.80, source=0.95, freshness=0.70, then U = 0.65×0.80 + 0.20×0.95 + 0.15×0.70 = 0.815.

8. Version Diffing and Change Detection

For laws, regulations, standards, policies, and academic working papers, “the newest page” is not always the version currently in force or appropriate to cite. A reliable pipeline tracks a canonical document identifier, publication date, effective date, amendment relationships, status, source authority, and the exact content hash.

Risk: an old version can remain searchableSearch indexes and vector stores may keep an older crawl until the next refresh. Duplicate URLs, cached copies, OCR variants, and consolidated versus amending documents can also compete in retrieval. Ranking by relevance alone can therefore surface a superseded text.
1
Identify the canonical recordUse official identifiers, issuing body, document type, and canonical URL—not title similarity alone.
2
Collect version metadataStore publication, effective, expiry, amendment, repeal, and consolidation information.
3
Normalize and compare textRemove layout noise, retain article structure, compute hashes, and diff meaningful additions, deletions, and replacements.
4
Update the index safelyInsert the new version, mark superseded entries, preserve lineage, and filter retrieval by the requested date or legal status.
Safer indexing rule for legal textDo not overwrite history. Keep version lineage and retrieve using an explicit as-of date or status filter. Cite the exact version and effective date used for the answer.

9. Noise Filtering and Context Packing

Before sending retrieved text back to the LLM, the harness may remove duplicated passages, advertisements, navigation, prompt-injection-like instructions, and unsupported claims. The remaining chunks must fit within a token budget together with system instructions, conversation history, the user question, and tool metadata.

Idealized context-selection problemOptimization idealization
Choose S to maximize total utility, subject to total tokens ≤ budget B.
C all candidate chunks
S chosen subset
U(c) utility of chunk c
t(c) token cost of chunk c
B available retrieval budget
Worked example. Budget B=700 tokens. A uses 320 tokens with utility 0.91; B uses 280 with 0.78; C uses 250 with 0.62. A+B uses 600 tokens and utility 1.69, so it fits. A+B+C uses 850 tokens, so it does not fit. A practical system may use a greedy or learned packing strategy rather than solving the exact optimization.

10. Generating a Grounded Answer

The LLM receives the assembled context and predicts the next token repeatedly. Retrieved text influences the answer, but it does not mechanically force truth. The model can still misunderstand a source, combine claims incorrectly, or cite a passage that does not support the sentence.

Next-token generation at inference timeStandard conceptual form
next token ~ P(token | previous tokens, instructions, question, selected documents)
I system and developer instructions
q user question
D_selected selected tool results
t≤k tokens generated so far
What improves grounding?Attach citations to specific claims, preserve source metadata, compare multiple sources, quote only the necessary evidence, distinguish facts from inference, and state when evidence is incomplete or conflicting.

11. Key Takeaways

Remember these six ideas

  1. LLM ≠ browser. External software performs network actions.
  2. Tool choice is implementation-dependent. It may come from model training, rules, a classifier, or a combination.
  3. Ranking formulas here are examples. Production systems often use learned retrieval and reranking models.
  4. Cosine similarity is not truth. It measures vector direction similarity, not factual correctness.
  5. OCR is uncertain. Preserve page images and review high-impact low-confidence spans.
  6. Grounding needs provenance and version lineage. Preserve sources, dates, status, limitations, and uncertainty through the whole pipeline.
Scope of this explainerThis page presents a common conceptual architecture. Individual products may use APIs instead of scraping, hybrid search instead of embeddings alone, or no explicit chunking at all.
